# 登录会话使用不透明令牌，服务端只保存摘要

状态：accepted

## 背景

认证需要在不引入 JWT 生态（密钥轮换、吊销黑名单、角色变更即时生效）的前提下，支持登出、禁用用户和修改密码后的即时失效。当前 `RedisAuthTokenStore` 保存令牌原文且不设置过期时间，令牌一旦泄露永久可用。

## 本轮收尾修订（2026-10-20 最新要求）

- 版本迁移与认证代码必须配套部署：先执行 `V28__user_auth_version.sql`，再确保所有承接请求的实例统一校验数据库状态/版本，禁止旧实例绕过校验。
- 无版本的旧 Redis 登录态不再按 0 兼容，需重新登录；此条取代下文旧的版本 0 兼容方案。保留旧键原 TTL，不清空共享 Redis。
- 2026-10-23 修订：登录与改密不再要求用户行锁协调或严格串行。改密在数据库事务内普通读取 User，校验旧密码及新密码规则并编码后，以同一 SQL 的 `WHERE id = ? AND auth_version = ?` 条件更新密码和递增版本。影响行数不是 1 时以 `409 RESOURCE_CONFLICT` 失败，不自动重试、不撤销 Redis 登录态；更新成功才撤销该用户全部 Redis 登录态，撤销失败仍回滚密码与版本。
- 登录沿用普通读取的 User 签发版本；接受并发登录返回立即失效的旧版本令牌，由认证过滤器查询数据库状态与版本拒绝其后续受保护访问。已通过认证的在途请求不承诺中断。主动退出仍只尽力撤销当前令牌。
- 以 `docs/api/common-contract.md`「本轮认证收尾修订」为准，取代此前底层管理能力验收计划：验证码、联系方式改绑、头像上传、管理员用户管理全部延期；本轮不新增 `UserService.setStatus` / `replaceRoles`、其实现或专属测试。下文禁用、重新启用及角色变更的规则仅作为延期设计保留，不属于本轮实现或验收范围。
- 此前无版本旧 Redis 登录态按 0 兼容的方案已被取代：读取时视为无效，受保护入口返回 401 重新登录，不因缺版本产生 500；显式非法版本仍保留安全拒绝处理，不补为 0。

## 决策

- 令牌由服务端用 `SecureRandom` 生成 256 位随机值并以 base64url 编码，不使用 JWT。
- Redis 只保存令牌的 SHA-256 摘要作为键，不保存令牌原文；校验时对客户端提交的令牌求摘要再查。摘要存储让 Redis 数据泄露不等于凭据泄露。令牌是高熵随机值，不存在字典攻击空间，因此用 SHA-256 而不是 BCrypt 这类慢哈希。
- 令牌有效期固定 7 天，自登录成功起算且不随请求续期；到期后必须重新登录。接口不返回过期时间，前端依赖 401 统一跳转登录。
- 令牌值是 JSON，保存 userId、角色快照及签发时的登录态版本（版本字段待实现）；角色快照用于构造 authorities，但不单独作为登录态有效的依据。
- 认证查库取舍（2026-10-20 确认，待实现）：有效令牌从 Redis 读取登录态后，认证阶段额外按用户主键查询数据库中的账号状态和当前登录态版本；用户不存在、账号不可用或版本不匹配时拒绝旧登录态。改密、禁用、角色变更与版本推进必须处于同一数据库事务，签发时的角色与版本也必须来自一致的状态，禁止用旧角色搭配新版本签发可用令牌。不带令牌的游客请求和主动退出不增加此认证查询；登录、注册依原业务流程处理，业务查询不计入认证查询。此决策取代原先“认证避免逐请求查库”的取舍，优先保证正确性；后续仅在测量到实际瓶颈后优化，不得无意放宽已确认的失效边界。Redis 撤销失败时改密、禁用、角色变更回滚的既定规则保持不变。认证查库时，已识别的数据库连接失败或超时导致无法确认身份有效性，必须拒绝访问并返回 HTTP 503、`SERVICE_UNAVAILABLE` 和安全默认文案，保留 requestId；前端保留令牌，不强制跳转登录。明确查到用户不存在、账号已禁用或登录态版本不匹配时返回 401。不得把 SQL 编程错误等所有数据库异常一律映射为 503，也不得在数据库不可用时退回仅信任 Redis 的认证方式。
- 登出尽力删除当前令牌；禁用用户与修改密码删除该用户的全部令牌，因此需要维护 userId → token 的反向索引。
- 主动退出的取舍（2026-10-20 确认，待实现）：前端调用退出接口并直接清除本地令牌，不等待服务端撤销结果。服务端仍尝试删除当前登录态；清理失败只记录带 requestId 的脱敏错误日志，不向用户展示内部故障、不要求用户重试退出。接受清理失败时令牌副本可能在原固定七天有效期的剩余时间内继续有效；不延长原 TTL。此语义是“本机退出 + 服务端尽力撤销”，不是服务端保证撤销。仅适用于主动退出，不放宽修改密码的强失效规则，也不能据此放宽禁用账号的失效要求。退出入口的认证特例（2026-10-20 确认，待实现）：仅 `POST /auth/logout` 不要求先解析出有效身份，认证过滤器不得因 Redis 登录态校验失败而提前阻断此入口；退出处理从请求携带的 Bearer 令牌中取得待撤销凭据，仅尽力撤销该令牌。不允许客户端指定用户 ID，不执行全端撤销。令牌已过期或不存在时正常结束，Redis 清理失败仅记脱敏日志。其他入口继续遵循认证依赖故障返回 503 的规则；缺失或格式错误的 Authorization 正常返回 HTTP 200、`{"data": null}`，不访问 Redis、不将格式不合法的内容作为令牌处理，也不记录凭据原文。对于已过期、不存在的令牌及已识别的 Redis 清理故障，同样使用该正常响应；该响应仅表示退出请求已处理，不保证服务端撤销成功，不掩盖其他未预期的程序错误。其他接口的凭据校验规则不变。
- 凭据校验失败统一返回"用户名或密码错误"，不区分账号是否存在。
- 登录态写入故障语义（2026-10-20 确认，待实现）：凭据正确但因已识别的 Redis 依赖故障无法确认新登录态及其反向索引成功保存时，登录失败，返回 HTTP 503、`SERVICE_UNAVAILABLE` 和安全默认文案，不向客户端返回新令牌，不伪装成凭据错误。若存在部分写入则尽力清理，记录脱敏诊断，不记录凭据原文；清理失败不改变本次登录失败的结果。
- 注册与自动登录的失败边界（2026-10-20 确认，待实现）：V1 将创建用户、关联默认角色和建立登录态视为一次完整操作；若已识别的 Redis 依赖故障导致无法确认登录态及反向索引保存成功，必须抛出异常，回滚新用户及角色关联，返回 HTTP 503、`SERVICE_UNAVAILABLE`，不返回新令牌。Redis 部分写入尽力清理并记录脱敏诊断；数据库事务不能自动回滚 Redis。数据库提交失败后的登录态也需尽力清理，不得将注册报告为成功。服务端已提交成功但响应丢失属于结果未知，不承诺账号未创建。本条明确目标语义，不代表跨存储一致性机制已完成。
- 禁用账号的强失效边界（2026-10-20 确认，待实现）：禁用成功后，新的认证检查必须拒绝该用户原有登录态，使用禁用前状态校验通过的并发登录也不得建立可用登录态；已经通过认证且正在执行的业务请求不承诺强制中断。若因已识别的 Redis 依赖故障无法保证上述失效效果，必须抛出异常，不提交禁用状态，返回 HTTP 503、`SERVICE_UNAVAILABLE` 及安全默认文案，保留 requestId；接受部分设备已被登出的副作用。不得将主动退出的尽力撤销规则用于禁用账号。协调机制与业务入口尚待实现。
- 认证依赖故障语义（2026-10-20 确认）：校验 Bearer 令牌时，若 Redis 连接失败或超时导致无法确认登录态，拒绝本次访问，返回 HTTP 503、`SERVICE_UNAVAILABLE` 及安全默认文案并保留 requestId；不得绕过认证，也不得将依赖不可用伪装成令牌失效。前端保留令牌，不因该 503 清除登录信息或强制跳转登录页。只有明确判定令牌无效（例如查无记录、已过期）时才按认证失败返回 401；缺失凭据、格式错误等仍遵循原认证规则。以上为待实现约定。

## 影响

- 多设备登录会同时存在多个有效令牌，修改密码后所有设备都需要重新登录。
- 版本升级：客户端令牌字符串和 Bearer 格式不变，存量用户版本初始化为 0，新签发登录态明确携带版本。**无版本旧登录态需重新登录**，不补成数据库当前版本或固定 0；显式 null、非法版本或损坏记录不能作为 0 接受。不清空整个 Redis、不延长原 TTL。迁移与代码配套部署，所有承接请求的实例都必须遵守版本校验。
- 重新启用账号的登录态边界（2026-10-20 确认，待实现）：重新启用只恢复登录资格，不恢复旧登录态，用户必须重新登录。此前因禁用而失效的令牌，即使尚未达到原过期时间或 Redis 中仍有残留记录，也不得重新可用。具体保证机制尚待确定。
- 修改密码的失效边界（2026-10-20 确认）：修改密码成功后，新的认证检查必须拒绝旧登录态；并发登录请求即使已用旧密码校验通过，也不得在修改密码成功后建立仍可用的旧凭据登录态。已通过认证且正在执行业务的请求不承诺强制中断。2026-10-23 已明确采用改密版本条件更新与认证查库兜底，不要求登录与改密严格串行；并发登录可以返回立即失效的旧版本令牌，但该令牌不能通过改密提交后的新认证检查。
- 修改密码失败语义（2026-10-20 确认）：因 Redis 故障无法保证旧登录态失效时，修改密码操作必须以异常失败，不提交密码更新，不返回成功；允许部分登录态已被清除这一副作用。不承诺客户端超时或响应丢失时密码一定未修改，后者属于结果未知场景。对外统一返回 HTTP 503、错误码 `SERVICE_UNAVAILABLE`，默认提示“服务暂时不可用，请稍后重试”，保留 requestId；内部记录脱敏诊断，不向客户端暴露 Redis 命令或内部异常信息。具体异常类与协调机制尚待实现。
- 固定有效期牺牲了活跃用户的登录连续性（第 7 天必然被登出一次），换取被窃令牌的可用窗口有明确上界；滑动续期下被窃令牌会被持续续期而永不失效。
- 角色变更的强失效边界（2026-10-20 确认，待实现）：增加或撤销角色成功后，必须使该用户全部旧登录态失效，要求重新登录获取新角色；并发登录不得在变更成功后建立带旧角色的可用登录态。若因已识别的 Redis 依赖故障无法保证失效，必须抛出异常，不提交角色变更，返回 HTTP 503、`SERVICE_UNAVAILABLE` 及安全默认文案，保留 requestId；接受部分设备已被登出的副作用。不承诺强制中断已经通过认证且正在执行的业务请求。此规则取代仅允许角色缓存短暂不一致的宽松描述；具体协调机制与业务入口尚待实现。
- 前端把令牌放在 `localStorage`：V1 没有 refresh token，内存存储会导致每次刷新页面都要重新登录，在选座到支付的流程里不可接受；作为交换，接受"令牌可被 XSS 读取"这一风险，由固定 7 天有效期与 CSP 等 XSS 防控兜底。令牌泄露后的兜底手段（refresh token、敏感操作二次验证）留到后续版本。
