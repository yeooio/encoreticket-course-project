# API 通用请求与响应契约

本文档定义所有 HTTP 接口共用的请求头、请求体、响应头、成功响应和错误响应格式。具体业务接口在没有特殊说明时，均遵循本契约。

## 1. 请求约定

### 1.1 通用请求头

| 请求头 | 是否必填 | 说明 |
|---|---|---|
| `Authorization` | 需要登录的接口必填 | `Bearer <accessToken>`；游客接口可以不传，若携带则由认证过滤器解析有效身份 |
| `Content-Type` | 有请求体时必填 | 固定为 `application/json` |
| `Accept` | 建议传递 | 固定为 `application/json` |
| `Idempotency-Key` | 明确采用该请求键契约的接口必填 | 由前端为一次业务操作生成并传入；创建订单、支付、退款等接口的既有约定见下文；同一次重试必须复用同一个值。当前电影、场次管理接口不要求 |

服务端生成 `requestId`，前端不需要在请求体中传递 `requestId`。`X-Request-Id` 是服务端响应头，详见响应约定。

**适用范围（2026-09-28 最新决定）：当前电影、场次低频管理接口，包括创建入口，暂不接入公共请求幂等表，也不要求 `Idempotency-Key`。** 前端关闭这些写请求的自动重试，以 `submitting` 提交锁阻止重复提交；超时或响应未知时标为“结果待确认”并查询业务结果。后端继续保留业务唯一约束、状态条件、版本和事务保护；不承诺重放首次成功响应。

以下幂等键生成、关联、重试和结果重放规则仅适用于**明确采用 `Idempotency-Key` 契约的接口**，不能据此推定所有写接口已经接入。订单、支付、退款和核销的业务幂等要求继续保留；本次管理接口调整不变更下文既有交易约定，具体请求键与业务编号方案在对应模块中确定。

`Idempotency-Key` 建议使用客户端生成的随机唯一字符串（例如 UUID），前端不能把订单号或支付单号直接当作幂等键。它不承担登录认证，也不能替代权限校验。

服务端应将幂等键与当前用户、接口路径和请求内容关联：

- 首次请求：执行业务并保存处理结果；
- 网络超时后重试：使用同一个 `Idempotency-Key`，服务端返回首次请求的结果；
- 相同幂等键但请求内容不同：返回 `409 Conflict`；
- 不同业务操作：必须生成不同的幂等键。

支付平台回调使用平台提供的通知流水号或事件 ID 做去重，不使用前端的 `Idempotency-Key`。

退款申请与管理员处理的已批准请求键、24小时快照及独立清理范围见 [退款接口](refunds.md)；退款结果未知不能以新键再次发起资金操作。

`Idempotency-Key` 不能替代后端业务去重。后端需要同时使用以下三层保护：

1. **幂等请求去重**：按用户、接口和 `Idempotency-Key` 识别同一次客户端重试，并返回首次处理结果；
2. **业务唯一性校验**：例如一张票只能存在一条成功核销记录，支付平台通知流水号不能重复处理；
3. **事务与并发控制**：通过事务、状态条件更新、唯一约束或必要的锁，防止并发请求绕过去重逻辑。

不能只使用业务编号去重：创建订单时订单号尚未生成；同一用户之后再次购买相同场次和座位可能是新的合法订单；支付和退款还需要区分不同的支付尝试或退款操作。业务编号和状态校验是后端的最终安全边界，`Idempotency-Key` 用于识别客户端重试并复用原始结果。

### 1.2 查询请求

查询条件和分页参数放在 URL Query 中，请求体为空。

```http
GET /screenings?page=1&pageSize=20&movieId=10001
Authorization: Bearer eyJ...
Accept: application/json
```

### 1.3 业务操作请求

业务字段直接放在 JSON 请求体中，不额外包裹 `data`。创建人、操作人、用户归属等敏感字段由服务端从登录态获取，前端不得传入并要求服务端信任。

```http
POST /orders
Authorization: Bearer eyJ...
Content-Type: application/json
Accept: application/json
Idempotency-Key: order_20260913_001
```

```json
{
  "screeningId": "10001",
  "screeningSeatIds": ["30001", "30002"]
}
```

订单输入使用选座响应的场次座位 `screeningSeatId`，不是物理 `seatId` 或展示编号。创建快照保留 24 小时、座位集合排序但重复输入拒绝、满期旧键可按新请求处理等已确认规则见[订单接口规格](orders.md)；四个订单入口已在后续授权中实施，具体实测事实及限制见订单规格第10节。

票券核销请求示例：

```http
POST /ticket-verifications
Idempotency-Key: checkin_20261019_001
Authorization: Bearer eyJ...
Content-Type: application/json
Accept: application/json
```

```json
{
  "ticketCode": "T202609130001",
  "screeningId": "10001"
}
```

### 1.4 字段格式

- JSON 字段使用 `camelCase`。
- 数据库 `BIGINT` 标识和业务编号以 JSON 字符串返回，避免前端数值精度丢失。
- 金额使用十进制字符串，例如 `"88.00"`，并同时返回 `currency: "CNY"`（接口需要展示金额时）。
- 时间使用带时区的 RFC 3339 格式，例如 `"2026-09-13T10:30:00+08:00"`。其中 `+08:00` 表示该时间比 UTC 早 8 小时，等价于 `"2026-09-13T02:30:00Z"`。当前影院业务默认使用中国大陆的 `Asia/Shanghai` 时区，因此示例使用 `+08:00`；它表示业务时间，不代表必须依赖部署机器的本地时区。
- 状态使用有业务含义的字符串，不使用数字枚举。例如返回 `"PENDING_PAYMENT"`、`"PAID"`、`"EXPIRED"`，不直接返回数据库中的 `0`、`1`、`3`。

时间格式和数据库存储类型是两层约定：数据库可以继续使用适合当前 MySQL 设计的时间类型，接口层负责统一序列化为带时区的字符串。系统时区按以下规则处理：

- 应用服务器、JVM 和容器的技术基准时区使用 UTC，获取当前时间使用明确的时钟，不依赖机器本地时区；
- 电影自动发行时间 `publishAt`、创建时间、更新时间、过期时间、支付通知时间和核销时间等技术时间统一按 UTC 计算和保存；
- 电影场次、售票开始和结束时间属于影院业务时间，当前按 `Asia/Shanghai` 解释并在接口中带上 `+08:00`；将来支持多地区影城时，应使用影城配置的时区，不能继续硬编码 `+08:00`；
- 接口返回时间必须带偏移量，前端可以根据用户或影城时区转换展示。

状态也可以在数据库中使用数字编码，但必须在 DTO/VO 转换时映射为稳定的业务状态字符串；HTTP 状态码与订单、支付、票券状态是不同概念。

## 2. 响应约定

### 2.1 通用响应头

服务端对成功和失败的每个 HTTP 响应都返回：

```http
X-Request-Id: req_20260913_abc123
Content-Type: application/json
```

`X-Request-Id` 用于将前端请求与服务端日志关联。它不是订单号、数据库主键或幂等键。该请求头属于行业常用的自定义约定；如后续接入分布式链路追踪，可增加 [W3C Trace Context](https://www.w3.org/TR/trace-context/) 的 `traceparent` 和 `tracestate`。

### 2.2 单条数据成功响应

HTTP 状态码使用 `200 OK` 或 `201 Created`，具体由接口语义决定。

```json
{
  "data": {
    "orderId": "10001",
    "status": "PENDING_PAYMENT",
    "totalAmount": "88.00",
    "currency": "CNY"
  }
}
```

### 2.3 列表成功响应

```json
{
  "data": {
    "items": [
      {
        "id": "10001",
        "name": "示例电影"
      }
    ],
    "page": 1,
    "pageSize": 20,
    "total": 1
  }
}
```

其中 `page` 从 1 开始，`pageSize` 表示本次请求的分页大小，`total` 表示符合条件的记录总数。

### 2.4 无数据成功响应

```json
{
  "data": null
}
```

## 3. 错误响应约定

错误响应不统一返回 HTTP 200，而是使用能够表达错误类型的 HTTP 状态码，并保持统一 JSON 结构。

```http
HTTP/1.1 409 Conflict
X-Request-Id: req_20260913_abc123
Content-Type: application/json
```

```json
{
  "code": "TICKET_ALREADY_USED",
  "message": "票券已核销",
  "data": null,
  "requestId": "req_20260913_abc123"
}
```

错误响应体重复返回 `requestId`，便于前端提示用户或客服反馈；成功响应体不重复返回该字段，前端从 `X-Request-Id` 响应头获取即可。

### 3.1 常见 HTTP 状态码

| 状态码 | 使用场景 |
|---|---|
| `400 Bad Request` | 请求格式错误或基础参数错误 |
| `401 Unauthorized` | 未登录、令牌缺失或令牌失效 |
| `403 Forbidden` | 已登录但没有接口权限 |
| `404 Not Found` | 目标资源不存在 |
| `405 Method Not Allowed` | HTTP 方法不支持 |
| `409 Conflict` | 状态冲突、重复操作或幂等冲突 |
| `415 Unsupported Media Type` | 请求媒体类型不支持 |
| `422 Unprocessable Entity` | 参数格式正确，但不满足业务规则 |
| `429 Too Many Requests` | 请求频率超过限制 |
| `500 Internal Server Error` | 服务端未预期的内部错误 |

### 3.2 前端处理要求

前端请求层统一处理以下字段：

```text
response.headers["x-request-id"]
response.data.data
response.data.code
response.data.message
response.data.requestId
```

业务页面只处理成功时的 `data`；错误提示、登录过期、权限不足和请求追踪信息由统一请求层处理。响应头名称不区分大小写，具体客户端库可能统一转换为小写。

### 3.3 基础错误码

错误响应中的 `code` 是稳定的业务错误标识，HTTP 状态码表示错误类别。前端逻辑应依赖 `code`，`message` 仅作为安全的默认展示文案。

| `code` | 默认 HTTP 状态 | 含义 |
|---|---:|---|
| `UNAUTHORIZED` | 401 | 未登录或登录已过期 |
| `FORBIDDEN` | 403 | 已登录但没有接口权限 |
| `INVALID_ARGUMENT` | 400 | 请求格式或基础参数不合法 |
| `RESOURCE_NOT_FOUND` | 404 | 请求的资源不存在 |
| `METHOD_NOT_ALLOWED` | 405 | 不支持当前 HTTP 方法 |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | 不支持当前请求媒体类型 |
| `BUSINESS_RULE_VIOLATION` | 422 | 请求不满足业务规则 |
| `RESOURCE_CONFLICT` | 409 | 资源已存在或当前状态冲突 |
| `HTTP_CLIENT_ERROR` | 400 | 容器报告的其他 4xx，请求无法处理 |
| `INTERNAL_ERROR` | 500 | 服务端未预期错误 |
| `SERVICE_UNAVAILABLE` | 503 | 已识别的依赖不可用导致操作无法安全完成；默认提示“服务暂时不可用，请稍后重试” |

默认错误码与 HTTP 状态的映射由后端异常处理器维护；具体领域错误码可以在后续业务实现中扩展，但应保持一个错误码对应一个稳定的 HTTP 状态类别。

容器 ERROR 分派保留实际的有效 400–599 状态。已列出的 400/401/403/404/405/409/415/422 使用对应基础码；其余 4xx（例如 406、413、429）使用 `HTTP_CLIENT_ERROR`，默认文案为“请求无法处理”。所有 5xx 使用 `INTERNAL_ERROR`，例如 503 仍保留 HTTP 503；表中的 400/500 是默认值，不把实际状态强制改为该值。业务异常的专用错误码继续由全局异常处理器维护。

2026-10-20 确认的待实现约定：修改密码时，若 Redis 故障导致无法保证旧登录态失效，必须抛出异常且不提交密码更新，通过应用异常映射返回 HTTP 503 和 `SERVICE_UNAVAILABLE`，响应保留 requestId。此约定不改变未分类容器 5xx 使用 `INTERNAL_ERROR` 的兜底规则，不将所有 Redis 异常无差别映射为 503；具体异常识别与映射尚待实现。

认证依赖故障约定（2026-10-20 确认，待实现）：Bearer 令牌校验期间 Redis 连接失败或超时，导致无法确认登录态时，拒绝访问并返回 HTTP 503、`SERVICE_UNAVAILABLE` 及安全默认文案，保留 requestId。不能绕过认证或将此故障映射为 401。前端保留令牌，不因该 503 清除登录信息或强制跳转登录页；明确查无令牌记录或令牌已过期时才按失效返回 401。缺失凭据、格式错误等其他认证场景仍遵循原有规则。

主动退出的特殊交互（2026-10-20 确认，待实现）：前端发起退出请求并直接清除本地令牌，不等待服务端结果；服务端尽力撤销当前登录态，撤销失败仅记录带 requestId 的脱敏错误日志，不向用户展示内部故障或要求重试退出。清除本地令牌不构成服务端撤销成功的保证；接受残留令牌在原有效期内仍可能可用。该取舍不适用于修改密码或禁用账号；仅 `POST /auth/logout` 不要求先验证出有效身份，认证过滤器不得因 Redis 登录态校验失败而提前阻断退出处理；该入口读取请求携带的 Bearer 令牌，仅尽力撤销该令牌，不接受客户端指定用户 ID 或撤销其他令牌。令牌已过期或不存在时正常结束，Redis 清理失败只记录脱敏日志；其他入口的认证故障仍返回 503。缺失或格式错误的 Authorization 正常返回 HTTP 200、`{"data": null}`，不访问 Redis，不将格式不合法的内容作为令牌处理，也不记录凭据原文；已过期、不存在的令牌及已识别的 Redis 清理故障同样返回该正常响应。此响应仅表示退出请求已处理，不保证服务端撤销成功，不掩盖其他未预期的程序错误。其他接口的凭据校验规则不变。代码尚未实现。

登录写入故障约定（2026-10-20 确认，待实现）：凭据校验正确，但已识别的 Redis 依赖故障导致无法确认新登录态及反向索引成功保存时，返回 HTTP 503、`SERVICE_UNAVAILABLE` 和默认文案“服务暂时不可用，请稍后重试”，保留 requestId，不返回新令牌，不作为用户名或密码错误处理。部分写入尽力清理并记录脱敏诊断，不能在日志或响应中暴露令牌；补偿失败不改变本次登录失败的结果。

注册与自动登录的失败边界（2026-10-20 确认，待实现）：创建用户、关联默认角色和建立登录态作为一次完整操作。已识别的 Redis 依赖故障导致无法确认登录态及反向索引保存成功时，抛出异常并回滚新用户及角色关联，返回 HTTP 503、`SERVICE_UNAVAILABLE` 和安全默认文案，保留 requestId，不返回新令牌；Redis 部分写入尽力清理并记录脱敏诊断。数据库提交失败不能报告注册成功，已写入的登录态需尽力清理。服务端已提交但响应丢失属于结果未知，不承诺账号不存在或重试一定成功；该约定不代表数据库事务能回滚 Redis。

禁用账号的失败边界（2026-10-20 确认，待实现）：禁用成功后，新的认证检查拒绝原有登录态，使用禁用前状态校验通过的并发登录也不得建立可用登录态；不承诺中断已经通过认证且正在执行的业务请求。若已识别的 Redis 依赖故障导致无法保证失效效果，必须抛出异常且不提交禁用状态，返回 HTTP 503、`SERVICE_UNAVAILABLE` 和安全默认文案，保留 requestId；接受部分设备已被登出的副作用。主动退出的尽力撤销规则不适用于禁用账号。

角色变更的失败边界（2026-10-20 确认，待实现）：增加或撤销角色成功后，使该用户全部旧登录态失效，要求重新登录；并发登录不得在变更成功后建立带旧角色的可用登录态，不承诺中断已经通过认证且正在执行的业务请求。若已识别的 Redis 依赖故障导致无法保证失效，必须抛出异常且不提交角色变更，返回 HTTP 503、`SERVICE_UNAVAILABLE` 和安全默认文案，保留 requestId；接受部分设备已被登出的副作用。

重新启用账号的登录态边界（2026-10-20 确认，待实现）：重新启用只恢复登录资格，不恢复旧登录态，用户必须重新登录。此前因禁用而失效的令牌，即使未到原过期时间或 Redis 仍有残留记录，也不得重新可用；不能仅凭账号状态恢复启用就接受旧令牌。

认证查库的故障边界（2026-10-20 确认，待实现）：认证从 Redis 读取登录态后，查询数据库账号状态与登录态版本。已识别的数据库连接失败或超时导致无法确认身份有效性时，拒绝访问，返回 HTTP 503、`SERVICE_UNAVAILABLE` 和安全默认文案，保留 requestId；前端保留令牌、不强制跳转登录。明确查到用户不存在、账号已禁用或登录态版本不匹配时返回 401。不得在数据库故障时降级为仅信任 Redis；SQL 编程错误等未预期异常不因此统一映射为 503。不带令牌的游客请求与主动退出不增加此认证查询，登录和注册按原业务流程处理。

登录态版本升级（2026-10-20 最新要求）：客户端令牌字符串及 `Authorization: Bearer <token>` 格式不变；存量用户版本初始化为 0。无版本旧 Redis 登录态需重新登录，不补为固定 0 或数据库当前版本，不延长原 TTL。新登录态明确携带签发时版本，非法或损坏记录不能作为版本 0 接受。代码与 V28 迁移配套部署，所有实例统一校验版本。

V1 范围取舍（2026-10-20 确认）：当前不考虑新增登录防暴力破解与登录限流，不将其列为本轮实现或验收要求。本轮亦不新增应用存活/就绪健康检查，不纳入实现或验收范围；不移除现有 Docker Compose 对 MySQL、Redis 的健康检查。契约中列出的 HTTP 429 仅为通用状态约定，不代表已实现限流；也不因此扩大为所有业务接口均无需限流的长期承诺。

### 本轮认证收尾修订（优先于上文待实现范围）

- 认证代码必须与 `V28__user_auth_version.sql` 配套部署，所有实例统一启用数据库账号状态及版本校验。无版本旧登录态需重新登录，取代上文缺省 0 的兼容计划；不清空共享 Redis、不续期。
- 登录/注册已携签发版本。2026-10-23 改密决策取代用户悲观行锁：保留数据库事务，普通读取 User，先校验旧密码及新密码规则，再编码，以 `WHERE id = ? AND auth_version = ?` 在同一 SQL 更新密码并递增版本；检查影响行数，非 1 返回 `409 RESOURCE_CONFLICT`，不自动重试、不撤销登录态。更新成功后撤销 Redis 全部登录态，撤销失败不提交密码与版本。

### 3.4 异常信息分层

基础请求日志范围（2026-10-20 确认，待实现）：本轮纳入 requestId 的 MDC 关联与统一请求耗时日志，不引入完整分布式链路追踪平台。请求处理期间普通业务日志自动携带当前 requestId，结束时清理或恢复原 MDC 值，防止线程复用串号；不承诺未经适配的异步任务自动传播上下文。请求摘要记录方法、脱敏路径、最终响应状态和耗时，不记录 Token、密码、完整请求体或查询参数原文。路径应优先使用不含具体参数值的路由模板，无法取得模板时不得直接将未经脱敏的原始路径作为摘要写出。ERROR 分派、异常退出和异步响应的完成时机、去重及状态记录方式需在实现前核对，不能将异常尚未映射的默认状态误记为最终状态。

- 后端日志记录 `requestId`、请求方法、原始路径、异常及其 cause/suppressed 的类型和栈帧，用于排查问题。同一请求内的同一异常去重，诊断深度和大小有界。
- 日志可补充 `ApplicationException` 的 ErrorCode 枚举 code 及默认说明、符合格式的 SQLState、数据库错误编号，以及 JSON 的有效数值行列。普通异常不读取或匹配原始 message，不维护固定文案白名单；每个异常节点独立筛选，不记录密码、令牌、完整请求体、原始 SQL/Redis 命令或源 JSON。文本截断和控制字符替换不等于敏感信息脱敏。
- 单条诊断总长度不超过 16,384 个字符，实际省略后续内容时附带计入上限的 `[diagnostic truncated]`；完整内容恰好达到上限时不标记截断。栈帧和异常图的独立上限继续使用对应提示。删除固定文案匹配会减少部分故障的文字原因，类型、栈帧、异常链和已有事件描述仍用于定位。
- 前后端契约使用稳定的 `code` 和 HTTP 状态码。前端应根据 `code` 判断处理分支，不应解析 `message` 的自然语言内容。
- `message` 是可安全展示的默认文案，必要时可由前端根据 `code` 映射为本地化提示。堆栈、SQL、Redis 命令和内部组件信息不得放入响应。
- 参数绑定失败时，使用受控字段提示，例如 `page: 格式不正确`，不返回框架转换原文、Java 类型名或被拒绝值。正常字段校验保留已确认来自项目 DTO 约束声明的固定文案；未知来源、非字段错误或动态字段路径使用通用校验提示。响应不得回显密码、令牌等字段的原始值。
- 服务端诊断的原因、错误编号和解析位置不会自动进入响应；系统异常仍返回 ErrorCode 的默认安全文案。

### 3.5 容器错误出口与保证边界

Filter 的未处理异常先转交 MVC Resolver；无法解析时继续传播，由容器 ERROR 分派进入应用 `/error`。该出口支持原始请求方法，返回 JSON，即使请求的 Accept 是 text/html；已有 requestId 会复用，缺失时补建。普通请求直接访问 `/error` 仍要求认证：匿名返回 401，已认证返回 404。

错误出口自身失败时不递归解析或反复写出。统一格式适用于应用能够接管且响应可写的 HTTP 错误；已经提交的响应、客户端断开、进程退出以及应用之前的协议拒绝无法保证完整 JSON。HEAD 错误响应保留状态和追踪头，不发送 JSON 正文。

当前 Servlet 6.1 容器把 ERROR 分派方法设为 GET，并在内部属性中保留原始请求方法。因此 POST/PATCH 等请求同样能够进入错误出口；日志使用原始方法。容器错误 JSON 使用 UTF-8。
