# 支付与退款的 Controller/Service 边界

状态：accepted

## 背景

支付和退款既包含用户可发起的操作，也包含支付通知、出票、异常退款处理等内部或管理操作。若把状态流转写入 Controller，容易导致订单、座位、票券和退款记录的更新分散，难以保证事务和幂等性。

## 决策

- `UserOrderController` 提供用户侧订单入口，以及订单关联的支付创建/查询和退款申请/查询入口。
- `AdminPaymentController` 提供管理员支付列表、详情和失败重试。管理员不能直接修改支付结果；模拟结果使用可信内部事件入口。若未来新增测试 HTTP 控制，仅 local/test Profile + ADMIN 注册，生产不注册。
- `AdminRefundController` 保留为管理员异常退款处理入口，负责退款列表、详情、明确失败重试和未知结果核查；不是人工审核或手工设成功入口。
- `OrderService`、`PaymentService`、`RefundService` 承载所有业务规则、数据归属校验、状态流转、事务边界和幂等处理。
- 支付成功后的订单状态变更、场次座位售出、票券生成，以及退款成功后的订单变更、票券作废、座位释放，均由 Service 协调，不由 Controller 直接修改。

订单四入口的正式规格见[orders.md](../api/orders.md)；当前订单 Controller 的退款子入口与独立 `UserOrderPaymentController` 是代码现状，不因本 ADR 的职责划分而承诺调整类归属。创建、列表、详情、取消仍待实现。退款受理自动执行、无人工审核；取消/过期迟到成功的补偿遵循 ADR 0001，不恢复权益。

## 结果

- 管理员异常处理能力保留，不会因为支付/退款逻辑归入 Service 而丢失 HTTP 入口。
- 普通用户接口和管理/测试接口的权限边界清晰。
- 支付、退款、订单、座位和票券的跨聚合状态更新集中在 Service，便于事务、幂等和审计。
- 后续实现时需要在 Controller 层分别配置用户、管理员和测试环境权限，不能仅依赖前端隐藏按钮。

## 不在本决策范围内

- 真实第三方支付渠道接入；
- 部分退款；
- 独立的支付回调网关 Controller；
- 管理员是否允许直接修改支付金额或订单金额。
