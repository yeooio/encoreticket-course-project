# 数据库设计与关系说明

以下依据本机 `encore_ticket` 数据库 information_schema 和项目 `docs/database/schema.sql` 核对。关系图是核心实体的简化示意，并非全部数据表和全部连线。数据库未建立物理外键，表间标识是逻辑关联；图中的 1、N 表示业务上的一对多，0..1 表示最多一条，不等于所有关系都由数据库外键强制。

- 用户与角色通过 user_role 连接；一个用户可对应多条用户角色记录，一种角色也可对应多条用户角色记录。
- 一部电影可安排多个场次；一个影厅可安排多个场次并包含多个物理座位。影厅与场次通过 `screening.hall_id` 逻辑关联，该关联未在简图中绘出。
- 一个场次可包含多个场次座位；一个物理座位可出现在不同场次的场次座位中。每个 `screening_seat` 对应一个场次及一个物理座位。
- 一个用户可有多个订单；一个场次可关联多个订单。每个订单只属于一个用户和一个场次。
- 一个订单有多个订单明细；每条明细关联一个场次座位。一个场次座位可能在不同时期关联多条历史订单明细，不能误标为永远一对一。
- 每条订单明细最多生成一张票券，`ticket.order_item_id` 具有唯一约束。成功核销记录最多一条，由 `ticket_verification.ticket_id` 的唯一约束保护；图中未画核销表。
- 一个订单可对应多条支付记录；`payment.order_id` 是逻辑关联，系统对成功支付另设唯一性约束。退款记录通过 `refund.order_id`、`refund.payment_id` 关联订单与支付；`refund.payment_id` 唯一，因此一条支付记录最多对应一条退款记录。图中未画退款表。
- 图中没有展示的其他表包括支付通知与审计、退款尝试与审计、模拟退款结果、接口幂等记录、Flyway 历史表。它们不能因简图省略而被误认为不存在。

`数据库实际字段.tsv` 是 2026-11-20 对本机库查询的信息，包含表名、字段名、类型、可空、键标记和字段注释。正式报告应逐表筛选核实字段、补充用途与三线表；该清单不是已经排版好的数据库设计章节。
