# 状态转换矩阵

本文档是当前业务状态图的文字基准。它描述状态、触发事件和关键前置条件，不展开具体接口实现流程。

数据库状态数字、Java 枚举和接口状态字符串的对应关系见[《状态枚举与数据库值映射》](status-enum-mapping.md)。

## 订单 `orders.status`

| 当前状态 | 目标状态 | 触发事件 | 前置条件与说明 |
|---|---|---|---|
| 无 | `WAIT_PAY` | 用户下单 | 每单购买同一场次的 1～6 个不同座位；订单和全部场次座位占用在同一事务中创建，任一座位不可售则整单失败，不部分占座 |
| `WAIT_PAY` | `PAID` | 支付成功 | 在订单过期前收到有效支付结果 |
| `WAIT_PAY` | `CANCELLED` | 用户取消 | 仅允许取消尚未成功支付且不存在结果未知的在途支付的待支付订单；取消本身不产生退款 |
| `WAIT_PAY` | `EXPIRED` | 订单超时 | 达到实际付款截止且尚未确认成功支付，释放该订单仍持有的场次座位；取消请求须即时检查截止，不依赖超时任务 |
| `EXPIRED` | `REFUNDING` | 收到迟到的支付成功通知 | 保留支付记录，自动创建退款；不恢复订单、不重新占座 |
| `CANCELLED` | `REFUNDING` | 确认取消后迟到收款成功 | 保留成功收款与取消历史，创建补偿退款；不重新占座、不出票 |
| `PAID` | `REFUNDING` | 退款申请受理 | 服务端受理校验时尚未达到开场前 15 分钟的退票截止，全部票券未核销且通过其他业务校验，仅支持整单退款 |
| `REFUNDING` | `REFUNDED` | 退款成功 | 支付渠道确认退款成功；有票券时作废，只释放本订单仍持有且符合释放条件的座位，补偿不得释放他人座位 |
| `REFUNDING` | `REFUNDING`（订单状态不变） | 退款失败 | 仅退款记录进入 `FAILED`，订单继续保持退款处理中，由管理员处理退款记录 |

`REFUNDED` 是终态。`CANCELLED` 不允许恢复为待支付或已支付，仅在确认迟到收款成功时允许进入 `REFUNDING`，随后按退款结果进入 `REFUNDED` 或由管理员处理失败退款。此例外不恢复购票权益、不重新占座、不生成票券，也不得释放已被其他订单重新占用或售出的座位；取消事实必须保留在历史记录中。

V1 不增加退款待审核状态。支付结果未知（`PENDING`）期间，不允许用户主动取消订单或申请退款，但不阻止订单按原付款期限自动过期。`PAID` 订单通过退票业务校验后受理整单退款；取消或过期后的迟到收款属于必须处理的补偿退款，不需要用户申请或人工审核。

用户发起取消时，须先在与支付、取消及过期变更互斥的条件下即时判断实际付款截止：对于仍为 `WAIT_PAY` 的订单，`now >= deadline` 时按过期处理，进入 `EXPIRED` 并释放该订单仍持有的座位，返回订单已过期的业务结果，不再写为 `CANCELLED`；存在 `PENDING` 支付也不阻止过期。只有未到期的待支付订单才继续检查主动取消条件。实际付款截止取创建后 15 分钟、`orders.expires_at` 与场次售票截止对应时间点的较早值。过期结果须实际提交，不能因返回业务错误而回滚；HTTP 状态与响应结构的建议默认见[订单接口规格](../api/orders.md)第 5 节，尚非逐项确认结论。

以上为已确认业务约定。取消入口及即时过期协议已在后续授权中实施；`CANCELLED` 迟到收款补偿已通过订单真实MySQL衔接测试，全部竞争交错仍须按订单规格实施记录区分，不能扩大为全覆盖验收。

退款失败不新增订单级 `REFUND_FAILED` 状态。订单状态描述订单生命周期，退款记录状态描述外部退款操作；管理员通过退款记录的 `FAILED` 状态判断是否需要重试。管理员重试成功后，退款记录进入 `SUCCESS`，订单再进入 `REFUNDED`。

### 订单领域不变量与接口规格索引

订单接口性质章节已迁移至[本人订单接口规格](../api/orders.md)：座位输入及全有全无见第 3 节，创建响应快照与 24 小时幂等见第 3.3 节，查询派生状态见第 2/4 节，取消按当前状态幂等见第 5 节，退票衔接见第 6 节。上述已确认规则逐项保留；HTTP、字段与分页等建议默认不等于新增业务确认或实现交付。

本矩阵保留领域基准：

- 每单同一场次 1～6 个不同座位，重复输入拒绝、不去重；后端验证场次归属、场次座位状态和物理座位可用性，原子创建并占座。
- 同用户同场次最多一个未到实际截止的 `WAIT_PAY`，并发也须成立；到期须实际过期释放后才可新购，不同场次与已支付不占名额，不构成累计限购 6 张。原请求的幂等重放不视为第二单。
- 创建后场次、座位与数量不可改；调整须合法取消后重新下单，不保证座位仍可买，不绕过 `PENDING` 限制，旧订单保留历史。
- GET 仅派生 `WAIT_PAY + 已到期 → EXPIRED` 展示，不写库、不释放；不能把查询状态作为释放依据，真实释放由写业务完成。
- 取消按当前状态幂等：`CANCELLED` 成功且不重复释放，`EXPIRED` 告知过期，`PAID/REFUNDING/REFUNDED` 冲突；`WAIT_PAY` 先判断截止，再判断在途支付。后续迟到收款进入退款后不重放旧取消成功。
- 用户新退票申请要求服务端受理时 `now < 开场前15分钟`、`PAID`、全部票券未核销及其他校验；恰好截止拒绝，已受理退款可继续完成，迟到收款补偿不受该截止限制。

四个订单入口已在2026-10-20后续授权中实施；实际验收范围及局限见订单规格第10节与交付报告，不能据矩阵视为所有并发/E2E已通过。

## 支付 `payment.status`

| 当前状态 | 目标状态 | 触发事件 | 前置条件与说明 |
|---|---|---|---|
| 无 | `PENDING` | 首次支付或管理员重试明确失败支付 | 管理员创建新记录并保留旧失败记录；订单必须仍可支付 |
| `PENDING` | `SUCCESS` | 支付渠道确认成功 | 支付通知必须幂等处理 |
| `PENDING` | `FAILED` | 当前渠道尝试明确失败 | 超时或结果未知时保持 `PENDING` |
| `FAILED` | `PENDING` | 用户明确失败后重付 | 复用原支付记录，新业务操作使用新幂等键与渠道尝试标识 |
| `PENDING` | `PENDING` | 再次提交或结果未知 | 返回现有记录，不重复发起渠道扣款 |
| `FAILED` | `SUCCESS` | 已知尝试的迟到成功 | 按服务器实际截止判断出票或创建待处理退款 |
| `SUCCESS` | `SUCCESS` | 重复通知或随后收到失败 | 不逆向覆盖成功结果 |

同键请求重放首次响应；查询接口读取当前状态。渠道通知以 provider/eventId 和规范化摘要去重；旧尝试失败不覆盖当前尝试。实际截止取下单后 15 分钟、订单 expires_at 与场次售票截止的较早值，达到截止即禁止付款。迟到成功不出票，释放剩余占座并创建退款记录，不表示退款已执行。重复支付通知不重复修改订单、座位或票券。

## 退款 `refund.status`

| 当前状态 | 目标状态 | 触发事件 | 前置条件与说明 |
|---|---|---|---|
| 无 | `PENDING` | 用户退款申请受理 | 或由迟到支付自动创建退款 |
| `PENDING` | `SUCCESS` | 支付渠道确认退款成功 | 订单进入 `REFUNDED` |
| `PENDING` | `FAILED` | 支付渠道明确拒绝 | 订单保持 `REFUNDING`，进入管理员处理 |
| `FAILED` | `PENDING` | 管理员重新处理 | 复用原退款业务记录重新发起 |

外部接口超时或结果未知时，退款记录保持 `PENDING`，只能查询原尝试或用相同渠道幂等标识恢复，不新建资金操作。受理自动执行全额原路模拟退款，无审核、不可撤回；管理员仅 FAILED 重试、PENDING 核查，不可手工设成功。来源和持久化恢复契约见 ../api/refunds.md。

## 票券 `ticket.status`

| 当前状态 | 目标状态 | 触发事件 | 前置条件与说明 |
|---|---|---|---|
| 无 | `VALID` | 订单支付成功 | 每个订单明细生成一张有效票券 |
| `VALID` | `USED` | 检票人员核销 | 票券、订单、场次均通过校验 |
| `VALID` | `VOID` | 退款成功或迟到支付退款 | 已生成票券时作废；未生成时不创建无效票券 |

`USED` 和 `VOID` 为终态，已核销票券不能再次退款或作废。

### 票券查询展示状态（不持久化）

`GET /tickets`、`GET /tickets/{ticketId}`、`GET /tickets/{ticketId}/status` 使用同一展示规则，详见[本人票券查询接口](../api/tickets.md)。下表是查询派生，不是对 `ticket.status` 增加状态转换或数据库编码；三个 GET 均不修改订单、票券或座位。

在必要关联及持久化状态合法的前提下，依次判定：

| 优先级 | 条件 | 展示状态 |
|---|---|---|
| 1 | 票券为 `USED` | `USED`，跨越结束时间仍保持终态 |
| 2 | 票券为 `VOID` | `VOID`，跨越结束时间仍保持终态 |
| 3 | 票券为 `VALID` 且订单为 `REFUNDING` | `REFUNDING`，即使场次已结束 |
| 4 | 票券为 `VALID`、订单为 `PAID` 且 `endTime <= now` | `EXPIRED`，包含恰好到达结束时间 |
| 5 | 票券为 `VALID`、订单为 `PAID` 且 `endTime > now` | `VALID` |

`EXPIRED` 表示票券已过场次，与订单占座超时的 `orders.status=EXPIRED` 含义不同。到期展示不依赖场次 `ENDED` 状态或调度写入。退款失败时订单保持 `REFUNDING`，查询不自动恢复票券；退款成功并作废票券后展示 `VOID`。

Service 每请求捕获一次注入的 Clock 时间，转换为 `Asia/Shanghai` 后供 SQL 状态筛选、count、select 与 Java 解析共用。场次时间输出 `+08:00`，核销及创建技术时间输出 UTC `Z`。查询不提供多语句或跨请求的一致快照；并发写入时 `total/items` 可能观察到相邻时刻的数据。

未知持久化状态、`VALID` 票关联非 `PAID/REFUNDING` 订单、已确认本人资源的必要关联缺失返回内部错误，不静默当作有效票。终态优先不豁免必要关联校验。当前断链后无法证明归属的票不会进入本人列表，单票查询返回 404；列表完整性预检查覆盖本人可归属票券，不受查询筛选限制，详见接口文档的限制说明。

展示 `VALID` 不代表必然允许入场。核销须独立校验订单、票券、场次及入场条件；退款受理与核销互斥、整单退款检查全部票券由对应写业务保证，不能据本查询功能宣称已完成并发或 E2E 验收。本次查询不新增缓存、数据库字段、状态编码或迁移。

## 电影 `movie.status`

| 当前状态 | 目标状态 | 触发事件 | 前置条件与说明 |
|---|---|---|---|
| 无 | `OFFLINE` | 管理员创建电影 | 保存自动发布计划与初始版本 0 |
| `OFFLINE` | `ONLINE` | 定时自动发布 | `publishAt` 非空且已到期；条件更新、清空计划时间、版本递增 |
| `OFFLINE` | `ONLINE` | 管理员手动发布 | `ADMIN` 携带当前 `version`；不受 `publishAt` 限制，允许提前或无计划发布；清空计划时间、版本递增 |
| `ONLINE` | `OFFLINE` | 管理员下架 | `ADMIN` 携带当前版本；清空自动发布计划、版本递增，避免下架后再次自动上架 |

手动发布沿用下架的状态冲突契约，不承诺重复请求成功：读取时已 `ONLINE` 返回
`409 MOVIE_ALREADY_RELEASED`（“电影已经上架”），优先于旧版本检查，不修改版本。
读取时 `OFFLINE` 但版本不匹配，或读取后自动发布/其他写入先递增版本，返回
`409 MOVIE_VERSION_CONFLICT`。手动发布采用乐观锁条件更新，自动发布保留既有
`OFFLINE + 到期计划` SQL 条件并递增同一版本，因此竞争不能覆盖另一方的成功写入。
发布改变目录可见性，不改变现实上映日期或关联场次生命周期。本次不增加状态、字段或数据库迁移。

## 影厅及物理座位维护

- Hall 与初始1～500个物理Seat原子创建，均 ENABLED；编号不可改、名称可重名，Seat位置不可改、不删除。
- ADMIN 携带独立编辑 version 可启停 Hall；允许存在未来场次，不取消或改写场次、订单、票券。停厅隐藏公开场次、禁止新排片/新开售/新下单，并禁止物理布局查询及Seat维护；厅详情/改名/重启允许。重启不主动重开场次，人工OFF_SALE不自动恢复。
- 追加Seat要求Hall启用且无任意关联场次，历史/关闭/已结束也阻止。
- Seat ENABLED→DISABLED：Hall启用，未关闭/未结束且endTime>锁后影院时间的场次没有该Seat的HELD/SOLD；已到期未释放HELD仍阻止，不清过期。允许全座停用，不自动停Hall。
- Seat DISABLED→ENABLED：Hall启用；不修改场次座位销售状态、不解除场次禁售、不补初始化遗漏席位。公开布局过滤停用Seat，人工/自动开售校验真实可售席位。
- 版本先于同状态判断；同版本同状态不写入，真实变化+1，旧版本冲突。Hall维护和排片共用Hall主键行锁，管理写先Hall→Seat；占售检查READ_COMMITTED非锁定读，不锁订单、不调用过期服务。
- 当前工作区订单侧已接Hall→Screening核心锁，并校验Seat启用和厅归属；属于并行订单模块实现，不归功于Hall。真实竞争未验收，不能宣称维护、占座、支付、过期、退款完整闭环；真实MySQL并发、隐式锁及死锁风险仍待授权验收。完整接口及限制见[影厅管理](../api/halls.md)。
